## 1. Core Validity Contract

**Tests MUST verify real behavior and MUST fail when production code is broken.**

- Every test asserts a meaningful outcome — not just that code runs without throwing
- If the production code logic is deleted or inverted, the test MUST turn red — a test that passes on broken code is worse than no test
- Do NOT write tests that only inflate coverage metrics (e.g., calling a method and asserting nothing, or asserting `assertNotNull(result)` as the sole check)
- **Unit tests:** mock only external dependencies (DB, HTTP, time), never mock the class/function under test itself
- **Integration tests:** mock only out-of-process external systems (third-party APIs, email), internal layers run real code

## 2. Testing Approach

Test through the PUBLIC contract ONLY. Do NOT use reflection to access private fields/methods unless absolutely impossible otherwise (last resort).

## 3. Arrange-Act-Assert (AAA)

Structure tests strictly into Arrange, Act, and Assert blocks separated by a SINGLE blank line.
**CRITICAL:** ZERO comments allowed to label these sections (no `// Given`, `// When`, etc.).

## 4. Test Redundancy & Coverage

Minimize duplicate tests without losing coverage metrics (lines, branches, statements).

- Merge duplicate scenarios using parameterized tests (`@ParameterizedTest`).
- Remove tests that provide ZERO unique coverage EXCEPT if they document a specific bug regression or compliance requirement.

## 5. Splitting Large Test Classes

If a test class exceeds 500 lines, SPLIT IT by public method being tested:

- Create directory `[classname]/` (lowercase).
- Create classes named `[ClassName][MethodName]Test.java`.

## 6. Refactoring for Testability

If production code is hard to test (e.g. SRP violations, deep nesting, lack of clear entry points), PROPOSE REFACTORING to the user before attempting to write complex, brittle tests to work around the bad design.

## 7. Integration Test Naming

Integration tests MUST end with `IT` or `IntegrationTest` (e.g., `MassStockControllerIT`). Do not use `Test` suffix for integration tests, so Gradle configuration properly separates them from unit tests.

## 8. Never Test Lombok-Generated Code

**NEVER** write tests for `equals`, `hashCode`, `toString`, getters, setters, or constructors generated by Lombok (`@EqualsAndHashCode`, `@Data`, `@AllArgsConstructor`, etc.). This is an antipattern — you are testing the library, not business logic. JaCoCo excludes this code automatically via `lombok.config` (`addLombokGeneratedAnnotation=true`). If JPA identity correctness matters, verify it implicitly through integration tests that use the repository.

## 9. Mockito `lenient()` — Use Only When Justified

**Default: strict stubs.** `@ExtendWith(MockitoExtension.class)` enables `STRICT_STUBS` — any stub that is set up but never called fails with `UnnecessaryStubbingException`. This is a feature: it catches dead test setup and reveals unnecessary dependencies.

**Use `lenient()` only in these cases:**

1. **`@BeforeEach` shared stubs** — a stub applies to all tests but is only exercised in some (e.g., a `findById` that every test needs except the "not found" case).
2. **Parameterized tests** — not every iteration takes every branch; some stubs will be unused in certain parameter combinations.
3. **Conditional code paths** — when the production code uses short-circuit evaluation (`||`, early `return`), a stub on a later branch will be skipped when an earlier branch triggers. Example: `isRequestContainingDisallowedFields` with `||` — a stub on a field checked late in the chain is legitimately lenient.
4. **Temporary during TDD** — while writing a test before all stubs are wired up. Remove `lenient()` once the test is complete.

**Do NOT use `lenient()` to silence Mockito on stubs that ARE always called** — that hides bugs. If the production code ever stops calling a dependency (e.g., someone removes a `repository.findById()`), strict mode catches it immediately; `lenient()` lets the test pass silently on broken code.

**Practical rule:** if you reach for `lenient()`, ask first — _can the stub ever NOT be called in this test?_ If the answer is "no", use `when()`. If "yes", `lenient()` is justified.
